## 1. 技术栈（终版）

| 组件 | 选型 | 理由 |
|---|---|---|
| L0 | **Astro**（静态输出） | Markdown → HTML，SEO 最好，产物就是一堆静态文件 |
| L1 | 纯静态文件 + **nginx Basic Auth** | 5 行配置，零代码 |
| L2 前端 | **Vite + React 19 (SPA)** | 你现有的栈；私密页面不需要 SEO |
| L2 后端 | **FastAPI** | 你最熟；这次它终于有了合适的位置 |
| 数据库 | **MySQL 8.0**（InnoDB） | 服务器上多项目共用的同一实例，边际成本为零 |
| 站内搜索 | **Pagefind** | 构建期静态索引，纯前端，零运行成本 |
| 加密 | Web Crypto API + `argon2-browser`(WASM) | 客户端，与后端无关 |
| 认证 | WebAuthn/Passkey + `py_webauthn` | L2 作者身份 |
| Web 服务器 | **nginx** | 按 `server_name` 分流 + Basic Auth + TLS |
| 证书 | **Let's Encrypt / certbot** | 免费，自动续期 |
| 进程管理 | **systemd** | 2C4G 上比 Docker 更省内存 |

### FastAPI 这次为什么可以用了

前两版否掉它，理由是"需要一个框架同时覆盖 SSG + 鉴权 + API"。

现在 **SSG 交给 Astro、鉴权交给 nginx**，FastAPI 只负责 L2 的密文 CRUD 和 WebAuthn——各司其职，反而最干净。你 Totur-Agent 那套 FastAPI + React + Vite 的经验可以整套搬过来，L2 基本没有新技术要学（除了 WebAuthn 和 Web Crypto）。

### 为什么改用 MySQL

之前推荐 SQLite 的前提是"这台机器只跑博客"。既然 MySQL **本来就要为其他项目常驻**，判断就反过来了：

- MySQL 的内存开销是**沉没成本**，博客用不用它都在那儿
- 用 SQLite 反而意味着同一台机器上跑两套数据库、两套备份策略、两套恢复流程
- 你正在系统学 MySQL，也有 Totur-Agent 的 MySQL 观测层经验——技术栈收敛到一处

**多项目共用一个 MySQL 实例的前提是隔离做对**：每个项目独立 schema、独立用户、权限只到自己的 schema。详见 ③ 第 2 节，这一条不做等于所有项目共享同一个爆炸半径。

## 2. 服务器资源规划（2C4G，多项目共存）

| 服务 | 常驻内存 | 说明 |
|---|---|---|
| 系统 | ~400 MB | Ubuntu / Alma 基础 |
| nginx | ~20 MB | 静态服务 + 反代 |
| **MySQL（调优后）** | **~800 MB** | 默认配置会更高，必须压 |
| FastAPI（uvicorn ×2 worker） | ~200 MB | L2 API |
| **小计** | **~1.4 GB** | |
| **剩余** | **~2.6 GB** | 分给其他项目 + 将来的 Totur-Agent demo |

CPU 2 核对静态站绰绰有余，L2 的 API 是个位数 QPS。

### 加了 MySQL 之后，内存需要认真规划了

之前 SQLite 方案剩 3.4 GB，随便放。现在剩 2.6 GB，还要分给其他项目——**这已经不是"随便放"的余量**。

两条硬建议：

**① 必须开 swap。** 阿里云实例默认没有 swap，一旦内存打满，OOM killer 会优先杀掉内存占用最大的进程——通常就是 MySQL，而且是静默杀掉，所有项目一起挂。

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10          # 尽量不用，只做保险
```

这是**保险，不是性能优化**。真触发 swap 说明该升配了，但有它至少不会突然全挂。

**② Totur-Agent demo 上线前先算账。** 如果它要加载本地 embedding 模型（bge-small ~500 MB，bge-base ~1.5 GB），加上 MySQL 和其他项目，4 GB 会很紧。到时候要么用 API 版 embedding 不加载本地模型，要么升配。

> **带宽仍然是另一个瓶颈。** 阿里云大陆实例常见 1–5 Mbps 峰值带宽，L0 的图片必须压缩（WebP / AVIF），避免大图直出。

## 3. 域名分流与证书

三个子域 = **三个独立 origin**，浏览器同源策略天然隔离：`lab.` 里任何 demo 的 XSS 都碰不到 `journal.` 的 API 和会话。

证书用 certbot 为三个域名签发（一张 SAN 证书涵盖三个，或各签一张）：

```bash
certbot --nginx -d yourdomain.com -d lab.yourdomain.com -d journal.yourdomain.com
certbot renew --dry-run          # 务必验证自动续期
```

HTTP-01 验证走 80 端口——备案已完成，80 可用，不需要 DNS-01 那套麻烦。

## 4. 目录结构

```
/srv/blog/                            # git 仓库
├── packages/
│   ├── public/                       # L0：Astro 源码
│   │   ├── src/content/posts/*.md
│   │   └── astro.config.mjs
│   │
│   ├── lab/
│   │   └── demos/<name>/index.html   # L1：静态 demo
│   │
│   └── journal/                      # L2
│       ├── web/                      # Vite + React SPA
│       │   ├── src/App.jsx
│       │   └── src/lib/crypto.js     # 客户端：派生/加解密/验签
│       └── api/                      # FastAPI
│           ├── main.py
│           ├── routes/entries.py
│           ├── routes/webauthn.py
│           └── db.py
└── deploy/
    ├── nginx/{public,lab,journal}.conf
    └── systemd/journal-api.service

/var/www/
├── public/                           # Astro build 产物
├── lab/                              # demo 静态文件
└── journal/                          # Vite build 产物

MySQL: 独立 schema `journal`，独立用户 `journal_app`（仅 DML 权限）
```

> **注意这里和前两版的一个根本差异：** Next.js 的 `public/` 会绕过 middleware，Cloudflare Pages 的 `*.pages.dev` 会绕过 Access——两者都需要专门防护。
>
> **nginx 没有这个问题**：`auth_basic` 写在 `server` 块上，该 server 下所有路径（含子目录里的 CSS/JS/图片）自动全覆盖。不需要把文件藏进什么 `private/` 目录。
