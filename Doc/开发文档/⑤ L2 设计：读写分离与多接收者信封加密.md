> **本章与托管方式完全无关。** 密钥派生、加解密、签名全部发生在浏览器里。三个版本的架构改来改去，这一章一个字都没变过——服务端在任何方案下都只是一个存取密文的哑接口。

## 1. 能力矩阵

| 角色 | 设备 | 认证方式 | 服务端返回 | 前端输入 | 读 | 写 |
|---|---|---|---|---|---|---|
| **作者** | 主力电脑 | Passkey `can_write=1` | 全部密文 | 主口令 | 全部 | ✓ |
| **作者** | 手机 | Passkey `can_write=0` | 全部密文 | 主口令 | 全部 | ✗ |
| **授权访客** | 他人电脑 | 访客口令 | **仅 `shared`** | 读口令 | 仅 `shared` | ✗ |

> **为什么"只读"不能靠加密实现**：AES-GCM 是对称算法，能解密就能加密。读者拿到密钥后，密码学上完全有能力造出合法密文。**写权限只能由服务端强制。**

### 手机为什么能看全部

手机也注册一个 passkey，但 `can_write = 0`。服务端认得这个凭据 → 返回全部密文；但写接口查到 `can_write=0` → 403。

代价是**在手机上要输主口令**才能解开 `private` 条目。这是有意的摩擦：手机丢了，捡到的人还要过 passkey（生物识别）+ 主口令两道。如果你觉得在手机上敲主口令太烦，退而只输读口令，那手机就只能看 `shared`——按你的习惯选。

## 2. 三套独立机制

| 问题 | 由谁解决 | 失效后果 |
|---|---|---|
| 谁能**读** | 加密层 —— DEK 包给了谁 | 内容泄漏 |
| 谁能**写** | 服务端 —— `credentials.can_write` | 他人可篡改 |
| 内容确实是**你**写的 | 签名层 —— Ed25519 | 被入侵的服务器可伪造条目 |

## 3. 密钥结构（多接收者信封加密）

```
KEK_owner  = Argon2id(主口令, salt_owner,  m=64MB, t=3, p=1)  → 256 bit
KEK_reader = Argon2id(读口令, salt_reader, 同参数)             → 256 bit

每篇日记：
  DEK        = getRandomValues(32B)                    每篇独立随机
  iv         = getRandomValues(12B)                    每次加密独立随机
  ciphertext = AES-256-GCM(JSON{title,body,tags}, DEK, iv)
  signature  = Ed25519(ciphertext ‖ iv ‖ created_at, sk_author)

  dek_owner  = AES-256-GCM(DEK, KEK_owner,  iv_o)      永远写入
  dek_reader = AES-256-GCM(DEK, KEK_reader, iv_r)      仅当 visibility='shared'
```

### 核心设计：`private` / `shared` 从源头分流，而非事后撤销

`private` 条目的 DEK **只包给 `KEK_owner`**。访客在**密码学层面就解不开**——不是"服务器不给你看"，是"把密文给你也没用"。

这比"先都能看、以后再撤销"强一个数量级，因为**撤销在密码学上根本不成立**：对方已经下载并解密过的内容，你永远收不回来。

> 落地建议：编辑器里 `visibility` 默认 `private`，改成 `shared` 需要显式勾选 + 二次确认。默认安全。
>
> 服务端再加一层：访客 session 的 GET 直接过滤掉 `private` 行，连密文都不发。纵深防御。

## 4. 密钥永不离开浏览器

口令、KEK、DEK、签名私钥**一律不发送给服务器**。FastAPI 收到的只有 `ciphertext / iv / dek_* / signature`。

- **签名私钥（Ed25519）**：仅存主力电脑，`IndexedDB` + `extractable: false` 的 CryptoKey
- **会话期内的 KEK**：只存内存变量，**不落 `localStorage` / `sessionStorage`**（XSS 可读）
- **草稿自动保存**：必须先加密再落地，不能图省事存明文

## 5. 恢复码（必须，不是可选项）

两个永久性失败场景：

- Passkey 绑设备 → 设备丢失或重装系统 = 永久失去写入身份
- 主口令遗忘 = 永久失去所有 `private` 内容

初始化时生成 32 字节随机恢复码，额外写入一份 `dek_recovery = AES-GCM(DEK, Argon2id(恢复码))`，**打印出来物理保存**。

> E2EE 的代价就是没有"找回密码"。这一步跳过，等于给自己埋一颗必然引爆的雷。

## 6. 写权限的唯一判据

**不要靠"手机上没有 Passkey"** —— iCloud 钥匙串和 Google 密码管理器**会自动把 passkey 同步到手机**，这层默认就是漏的。

硬判据：断言成功后，服务端再查一次 `credentials.can_write`。

```python
# routes/entries.py
@router.post("")
async def create_entry(req: Request, body: EntryIn):
    sess = require_session(req)              # 1. 有没有有效 session
    cred = get_credential(sess.cred_id)      # 2. 是哪个凭据建立的
    if not cred or not cred.can_write:       # 3. 这个凭据有没有写权限
        raise HTTPException(403)
    ...
```

**第 3 步是关键。** 缺了它，手机同步过去的 passkey 一样能写。注册主力电脑时手动把 `can_write` 置 1，其他设备一律 0。

## 7. 读口令轮换

共享口令的固有弱点：**一人泄露，全员泄露**。轮换流程：

1. 新读口令 → 派生 `KEK_reader'`
2. 用 `KEK_owner` 解出所有 `shared` 条目的 DEK
3. 用 `KEK_reader'` 重新包一遍 `dek_reader`
4. `crypto_params.key_epoch += 1`

**正文密文无需重新加密**（DEK 没变），只重包封套，几百条也是秒级完成。

建议：半年一轮换，或访客名单变动时立即轮换。同时换掉 `/api/session` 的访客口令。

> 如果以后需要"不同人看不同内容"，升级路径是给每位访客一对 X25519 密钥、DEK 逐人包一份。数据模型上只需把 `dek_reader` 单列改成一张 `entry_recipients` 子表，正文层完全不动——现在选共享口令不会造成返工。

## 8. 签名不是可选项

服务器被入侵时，攻击者读不到内容（有加密），删除也看得出来（条目消失），但**能往你的日记里插入伪造条目**。

读者端验签是唯一能发现这件事的手段：公钥存 `signing_key` 表，前端渲染前逐条验签，**失败时红色告警，而不是静默展示**。
